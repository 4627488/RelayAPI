# Agent Note: Pin latest pnpm 11 for web installs

Status: implemented

## Problem

Unpinned `corepack enable` on `node:24-alpine` activates pnpm 11. Frozen lockfile installs then fail with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` because pnpm 11 defaults `minimumReleaseAge` to 1440 minutes and this repo commits same-day lockfile upgrades (`rolldown@1.2.6`, `eslint-plugin-react-refresh@0.5.5`, `systeminformation@5.33.4`). CI used pnpm 10, so only the image job failed.

## Decision

Pin the current `latest` tag, `pnpm@11.24.0`, in CI, both Dockerfiles, `.cursor/install.sh`, and `web/package.json` `packageManager`. Copy `pnpm-workspace.yaml` into the image before `pnpm install` so Docker sees the same settings. Set `minimumReleaseAge: 0` there: image CI runs on the same commit that updates the lockfile, so a 24-hour cooling-off window cannot pass.

## Alternatives considered

**Stay on pnpm 10.** Avoids the new default, but leaves Docker/CI/dev on a stale major while Node 24 already ships 11.

**Keep `minimumReleaseAge: 1440` and exclude today's packages.** The next vite/rolldown or shadcn bump fails image CI again.

**Wait 24 hours after every lockfile bump.** The image job is part of the same PR; waiting is not a merge policy.

## Consequences

Web installs use one exact pnpm version. Bumping pnpm is an explicit pin change. Same-day dependency upgrades can ship in the image job. A later desire for a cooling-off window has to come with a delayed image build, not a lockfile committed in the same change.
